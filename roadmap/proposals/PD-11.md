# PD-11: authenticated host projection and native provider routing

Status: Accepted; phase 1 implemented

Depends on: none for phase 1; later phases integrate
[PD-3](PD-3.md), [PD-4](PD-4.md), [PD-5](PD-5.md),
[PD-6](PD-6.md), and [PD-7](PD-7.md)

Back to the [roadmap](../../ROADMAP.md#accepted).

## Decision summary

Add one canonical host projection before program loading. The projection is an
atomic, bounded, provenance-bearing inventory of the invoking host facilities
that JOSH may bind to one connection. It accounts for tools, resources,
attachments, transcript access, models, user interaction, agents, roots,
permissions, limits, and telemetry.

Discovery does not grant authority. A projection states what the host can
describe and route. `execution/start` continues to carry the exact authority
grants for one selected program and entry.

Phase 1 adds the `josh.host-projection/0.1` wire contract, honest session
binding levels, per-section completeness metadata, a canonical projection
digest, tool-catalog binding, exact required-tool reporting after program load,
and an injectable MCP bridge adapter. Later phases replace prompt-assisted
provider forwarding with host-native routing and add resource, artifact, A2A,
AG-UI, MCP 2026, and telemetry adapters.

## Product objective

An agent host should be able to give JOSH a complete, least-authority view of
the current task environment without asking the model to reconstruct that
environment from its prompt. An agent can then write or select an ALLEN
program against exact typed contracts, review the requested authority, run the
program, and receive one validated result.

The projection supports two use modes:

1. An ephemeral agent-written program names exact tools from the frozen host
   catalog.
2. A reusable package declares typed interfaces that a later PD-5 negotiation
   phase binds to compatible projected implementations.

## Projection layers

The architecture keeps four concepts separate.

| Layer | Content | Freeze or decision point |
|---|---|---|
| Contract projection | Tool, model, agent, and provider interfaces | Before program loading |
| Context projection | Transcript, resource, and attachment references | Before execution, with lazy content access |
| Authority projection | Tools, roots, resources, and effects granted to one entry | `execution/start` |
| Runtime routing | Native handlers for provider calls, cancellation, and events | Bound for the execution lifetime |

Automatic projection MUST NOT imply automatic disclosure, invocation, or
mutation authority.

## Phase 1 wire contract

The host sends `host/project` after `initialize` and before `catalog/set`.
The request contains:

- profile `josh.host-projection/0.1`;
- one opaque projection ID;
- the projecting host identity;
- one honest session binding level;
- exactly ten canonical section records; and
- source, revision, observation time, freshness, completeness, and item count
  for each section.

The canonical sections, in order, are:

1. `tools`
2. `resources`
3. `attachments`
4. `transcript`
5. `models`
6. `user_interaction`
7. `agents`
8. `roots`
9. `permissions`
10. `telemetry`

Session binding is one of:

- `none`: no invoking session is bound;
- `prompt_assisted`: an adapter can return work to the current prompt but does
  not authenticate the invoking actor; or
- `authenticated`: the host contract binds one authenticated invoking actor
  and session.

Unattended initialization requires `none`. Attached initialization requires
`prompt_assisted` or `authenticated`. A prompt-assisted bridge MUST NOT claim
authenticated identity or issue identity receipts.

JOSH validates the shape and computes the projection digest itself from the
canonical request. A supplied digest is never trusted. The successful result
echoes the validated projection plus the computed digest.

Phase 1 defines canonical encoding as compact UTF-8 JSON serialization of the
strictly decoded typed request in declared struct-field and canonical section
order, followed by SHA-256. This is deterministic for the fixed phase-1
structure; it is not a general JSON canonicalization scheme.

Phase 1 deliberately does not add `projection_digest` to execution accepted
events, artifacts, or replay bindings. Its scope is the frozen connection
projection and the immediately verified tool-catalog match. A later contract
revision must bind the digest before projected non-tool context or authority
can affect an execution or replay; no implementation may infer that binding
from the phase-1 digest alone.

The subsequent `catalog/set` metadata and tool count MUST equal the `tools`
section. A mismatch rejects the catalog without freezing partial state.

## Coverage and schema compatibility

Completeness means that the producer accounted for the complete section under
its declared policy. It does not mean that every discovered item is usable by
ALLEN.

Later inventory payloads will classify each discovered item as:

- typed and projected;
- rejected because its schema is incompatible;
- withheld by host policy;
- unavailable until authentication; or
- unsupported by the current adapter.

The host may expose counts for policy-visible classes. It MUST NOT represent a
compatible subset as a complete source inventory. An incompatible tool never
creates an untyped `call(name, json)` escape hatch.

## Bridge injection contract

The packaged bridge keeps a small built-in projection for its integration
tool. A native host adapter can replace it through a host-owned projection
file. The file contains the exact `host/project` request, the complete
`catalog/set` request, and the tool names that host policy authorizes for this
bridge execution.

The bridge:

1. reads and bounds the file before launching JOSH;
2. sends `host/project` and waits for its validated result;
3. sends `catalog/set` and waits for catalog freezing;
4. loads the program;
5. reads the exact required tools returned by `program/load`;
6. intersects those requirements with the host-owned grant list; and
7. starts execution with only that intersection.

The bridge never searches source text to infer a grant.

## Native routing phases

The accepted adapter mapping is:

| JOSH route | Preferred integration |
|---|---|
| `tool/invoke` | Native host registry or MCP tool provider |
| `model/request` | Native model route or MCP multi-round-trip input |
| `user/ask` | Native UI, MCP input request, or AG-UI interaction |
| `agent.*` | Authenticated native invoking-session binding |
| `sub_agent.*` | Native child agent or selected A2A agent task |
| transcript and resources | Host projection with typed opaque references |
| execution events | Native activity UI, AG-UI, and OpenTelemetry |

Manual `next_action` forwarding remains a compatibility and diagnostic mode.
It is not the target native integration.

## Reusable workflow export

A later phase adds `josh serve-mcp <package>`. Each exported ALLEN entry becomes
one typed MCP tool. The entry input and output contracts become tool schemas,
and a JOSH application handle carries any multi-round-trip execution state.
The same package can later expose selected entries as A2A skills.

This creates the intended lifecycle:

1. An agent encounters repeated bounded work.
2. The agent writes and tests an ALLEN workflow.
3. The workflow is recorded and replayed.
4. The package is exposed as a reusable agent tool.
5. Later agents call the compiled workflow without regenerating its policy.

## Accepted delivery phases

1. Canonical projection contract and conformance tests.
2. Complete native tool-catalog projection and exact dispatch.
3. Native callback routing for model, user, agent, sub-agent, transcript, and
   permission providers.
4. MCP `2026-07-28` stateless and multi-round-trip adapter, with optional Tasks
   extension support.
5. Typed context, resource, attachment, root, and artifact projection.
6. ALLEN-package-as-MCP-tool export.
7. A2A agent discovery and task provider.
8. AG-UI activity projection and OpenTelemetry export.
9. PD-4 identity receipts and PD-2 mutation-safe retry integration.

## Required tests

Phase 1 must test:

- every missing, duplicate, reordered, incomplete, or invalid section;
- unattended and attached session-binding combinations;
- canonical digest stability;
- catalog source, revision, freshness, observation time, completeness, and
  count mismatches;
- program-load exact required-tool reporting;
- bridge rejection of malformed, partial, oversized, or unauthorized injected
  projections;
- grant selection from verified artifact requirements rather than source text;
  and
- protocol state rejection when projection is skipped, repeated, or sent after
  catalog freezing.

Later phases add hostile-provider, cancellation, resource disclosure,
identity, receipt, adapter-version, and cross-protocol conformance tests.
