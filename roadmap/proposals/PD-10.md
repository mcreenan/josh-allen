# PD-10: opt-in Executor CLI tool provider

Status: Implemented MVP

Depends on: None

Back to the [roadmap](../../ROADMAP.md#implemented-mvps).

## Decision summary

The shipped MVP adds an opt-in Executor CLI provider to `josh run`. The
provider dispatches an already typed and granted ALLEN tool through a
user-installed and configured `executor` command.

The MVP uses the current ALLEN `0.1` tool model and the current `josh/1.5`
protocol. It does not add dynamic tool lookup, automatic catalog import, or a
new language effect.

The user opts in with `--executor`, supplies a complete JOSH tool catalog, and
grants each tool by exact name. Without `--executor`, `josh run` keeps its
current behavior and rejects `tool/invoke` as unavailable.

## Problem

Before this MVP, `josh run` could freeze a typed catalog and compile an ALLEN
program against it, but it granted no tools and rejected every runtime
`tool/invoke` request. A catalog proved a compile-time contract without
supplying a local tool executor.

An attached agent host can service `tool/invoke`, but that route may require an
agent turn and another model call. The extra turn adds latency even when the
tool name, input, schema, and authority are already fixed.

Executor provides a local CLI backed by the user's configured integrations,
credentials, and policies. JOSH can use that CLI as one concrete tool provider
without giving ALLEN an untyped Executor code operation.

## Scope

The implemented MVP adds:

- An explicit `--executor` provider selection for `josh run`.
- A repeatable `--grant-tool <name>` option.
- Exact dispatch from a JOSH `tool/invoke` request to `executor call`.
- Bounded JSON input and output handling.
- A fixed Executor error projection that fits `allen.tool-schema/0.1`.
- Deadline enforcement and best-effort child-process cancellation.
- Fail-closed handling for approval, authentication, and other paused calls.
- Focused conformance, security, and CLI tests.
- Agent documentation for the new execution route.

The implemented MVP does not add:

- Automatic discovery or import of the Executor catalog.
- Parsing of human CLI help or TypeScript previews into schemas.
- Direct reads from Executor's private database or credential files.
- Executor's code-mode `execute` tool as an ALLEN operation.
- Runtime calls by a dynamic name or untyped JSON escape hatch.
- Automatic approval, browser interaction, or `executor resume`.
- Schema conversion for arbitrary OpenAPI, GraphQL, or MCP tools.
- Tool-version inference from an Executor address or schema.
- An agent-host fallback after Executor failure.
- Exactly-once mutation, durable execution, or signed receipt claims.

## Terms

The Executor CLI is the installed `executor` command selected from the
runner's inherited `PATH`.

The Executor CLI provider is the `josh run` adapter that services one typed
JOSH `tool/invoke` request by starting `executor call`.

An Executor address is the dotted tool path accepted by `executor call`.

An exact tool grant is one canonical tool name supplied through
`--grant-tool`. The same string is the JOSH catalog name and Executor address.

Deterministic dispatch means that the provider selects the command, address,
and input without a model or agent decision. It does not mean that the remote
service result or external side effect is deterministic.

A paused call is an Executor execution waiting for authentication, approval,
or another user interaction.

## Concrete example: read one issue

The user has Executor installed and has configured one GitHub connection. A
catalog file contains an ALLEN-compatible definition for the exact Executor
address `github.org.main.issues.get`.

The ALLEN package declares the same tool:

```toml
[[tools.required]]
name = "github.org.main.issues.get"
version = ">=1.0.0, <2.0.0"
```

The program calls only the generated typed operation:

```allen
let issue = await tools.github.org.main.issues.get.call({
  owner: input.owner,
  repository: input.repository,
  number: input.number,
})?;
```

The user runs:

```sh
josh run \
  --executor \
  --catalog executor-github.json \
  --grant-tool github.org.main.issues.get \
  --input @issue-input.json \
  issue-report.allen
```

The runner freezes the supplied catalog, loads the program, and grants only
the named tool. When JOSH sends `tool/invoke`, the runner starts the equivalent
argument vector:

```text
executor
call
github.org.main.issues.get
@<secure-temporary-input-file>
```

The runner does not invoke a shell. The Executor process reads the exact JSON
object from the temporary file and applies its configured connection and
policy.

If Executor returns a successful tool result, JOSH validates `data` against
the frozen output schema before ALLEN receives it. If Executor returns an
expected tool error, the provider projects that error into the fixed declared
error shape and JOSH validates it before ALLEN receives it.

## CLI contract

The implemented command additions are:

```text
--executor                 Dispatch typed tool calls through the installed Executor CLI
--grant-tool <name>        Grant one exact declared tool; repeat for more tools
```

`--executor` has no effect on filesystem, HTTP, model, user, invoking-agent, or
sub-agent providers. Standard capability grants continue to use `--grant` and
`--allow-net-origin`.

The MVP provider is available on Unix hosts. A non-Unix runner rejects a
nonempty `--grant-tool` set before entry execution because the required
user-only temporary-file modes and descendant process-group termination are
not both available through the current safe implementation.

The runner applies these preflight rules:

1. Every `--grant-tool` value is a canonical JOSH tool name.
2. Every granted name exists in the frozen catalog.
3. Program preflight rejects a granted name that the artifact does not
   declare.
4. An entry that can call a required tool receives authority only when that
   exact name is granted.
5. `--grant-tool` without `--executor` is a CLI argument error.
6. When at least one tool is granted, the runner checks that `executor` exists
   before starting the ALLEN entry.

The MVP does not silently grant every catalog entry. Catalog membership is a
type contract. It is not execution authority.

## Catalog contract

The user or invoking automation supplies the catalog through the existing
`--catalog` option. The catalog must already satisfy the current JOSH limits
and `allen.tool-schema/0.1`.

For the MVP, each Executor-backed definition follows these additional rules:

- The catalog name is the exact Executor address.
- The input schema has an object root because `executor call` accepts a JSON
  object as tool input.
- The output schema uses only the current ALLEN tool-schema profile.
- The catalog supplies the exact semantic version. The provider does not infer
  one from Executor.
- The declared error schema is the fixed adapter shape below.
- Effects and idempotency metadata are catalog claims. Executor policy does
  not prove them.

The fixed declared error schema is equivalent to:

```json
{
  "type": "object",
  "properties": {
    "code": {
      "type": "string",
      "minLength": 1,
      "maxLength": 128
    },
    "message": {
      "type": "string",
      "minLength": 1,
      "maxLength": 2048
    }
  },
  "required": ["code", "message"],
  "additionalProperties": false
}
```

The provider rejects a granted catalog entry with a different declared error
digest. This rule prevents a generic Executor error from being misrepresented
as a tool-specific domain error.

Catalog metadata with `complete: true` describes the complete set offered by
this JOSH host configuration. It does not claim to enumerate every tool in the
user's Executor installation. Only cataloged and explicitly granted addresses
are available through the provider.

## Provider dispatch

The `josh run` process acts as the host-side protocol client for its child
`josh serve` process. With `--executor`, that client services `tool/invoke`
instead of rejecting it.

For each invocation, the provider:

1. Parses and validates the JOSH request.
2. Checks the exact grant and frozen catalog entry.
3. Checks the tool version and catalog digest carried by the invocation.
4. Encodes the validated input as bounded JSON.
5. Creates a private temporary directory and an input file with user-only
   permissions.
6. Starts `executor` directly with an argument vector.
7. Reads bounded stdout and stderr while enforcing the operation deadline.
8. Parses one supported Executor result.
9. Deletes the temporary file and directory.
10. Returns a JOSH tool result or one stable provider error.

The provider never constructs a command string. Tool names and file paths
remain separate process arguments. Shell metacharacters in a tool name cannot
start another command.

The provider inherits the normal process environment because Executor uses the
user's existing local configuration. JOSH does not read or copy Executor
credentials.

## Outcome mapping

The MVP accepts these completed Executor values:

```json
{
  "ok": true,
  "data": {}
}
```

```json
{
  "ok": false,
  "error": {
    "code": "not_found",
    "message": "Issue not found"
  }
}
```

The provider maps them as follows:

| Executor result | JOSH result |
|---|---|
| `ok: true` | `ToolInvokeResult::Ok` with `data` |
| `ok: false` with bounded `code` and `message` | `ToolInvokeResult::Error` with the fixed error projection |
| Missing executable | `tool.unavailable` |
| Any nonzero CLI exit | `tool.unavailable` with a stable message |
| Invalid or oversized JSON | `tool.unavailable` with a stable message |
| Deadline elapsed | `tool.unavailable` with a stable message |
| JOSH grant rejection | `tool.denied` |
| Structured Executor policy error | Fixed declared error projection |
| Human-readable pause or resume instructions | `tool.unavailable` |

The provider does not expose raw stderr, stack traces, credential paths, or
Executor configuration details to ALLEN source.

JOSH remains responsible for validating successful output and declared error
values against the frozen schemas. A value that fails validation becomes the
current generated tool schema error.

## Approval and user interaction

The MVP does not drive Executor approval or authentication flows. It never
runs `executor resume`, opens a browser, or changes Executor policy.

If a call pauses, the provider returns a safe unavailable result and ends that
tool attempt. The user can complete setup or change policy outside JOSH, then
start a new execution.

This rule avoids holding an unattended JOSH process open while waiting for an
unbound human decision. A later proposal revision may add structured pause and
resume only after Executor exposes a stable machine-readable contract and the
JOSH lifecycle defines who owns the wait.

## Deadlines and cancellation

The provider uses the smaller of the JOSH operation deadline and the remaining
execution wall-time limit. It kills the CLI child when that deadline expires.

Cancellation is best effort. Killing the CLI process does not prove that an
upstream mutation stopped or failed to commit. The Executor daemon or remote
service may have accepted the request before JOSH cancelled its local wait.

The MVP therefore makes no automatic retry after timeout, process loss, or an
ambiguous result. PD-2 defines the future mutation and reconciliation rules.

## Determinism and replay

The provider makes dispatch deterministic with respect to the frozen JOSH
catalog, exact tool grant, tool name, and input value. No model selects or
rewrites the call.

Live tool output remains an external effect. Recording stores the validated
boundary result under the current replay contract. Replay returns the recorded
result and must not start Executor again.

Executor's own catalog can change after JOSH freezes its catalog. The MVP does
not claim a shared snapshot or revision lock across the two systems. JOSH still
validates every returned value against its frozen schema, but it cannot prove
that Executor invoked the same upstream definition. Automatic import and
cross-system revision binding require a later machine-readable Executor
contract.

## Security rules

- Executor dispatch is disabled unless the user passes `--executor`.
- The runner never falls back to an agent, model, shell, or untyped code tool.
- A tool must pass catalog, manifest, entry-effect, and explicit-grant checks.
- Executor policy may narrow authority further. JOSH cannot override a deny or
  approval requirement.
- The provider invokes the exact `executor` binary resolved from `PATH`.
- Tool input does not appear in the process argument list.
- Temporary input files use user-only permissions and bounded contents.
- Stdout and stderr have independent byte limits.
- Public errors contain no raw tool input, output, paths, credentials, or
  Executor response bodies.
- The provider does not interpret CLI output as shell syntax, source code, or a
  new tool request.
- A timeout or killed child does not authorize a retry.

## Failure cases

Preflight or execution fails safely when:

- `--executor` is absent and the entry needs a tool.
- The `executor` command is not installed or cannot start.
- A granted name is invalid, absent from the catalog, or undeclared by the
  artifact.
- A required tool is not explicitly granted.
- A catalog error schema differs from the fixed Executor error projection.
- A catalog input schema does not have an object root.
- Executor returns a nonzero exit.
- Executor prints human-oriented approval or authentication instructions.
- Output exceeds the provider or protocol limit.
- The invocation deadline expires.
- The result fails its frozen output or declared-error schema.
- The JOSH connection closes before the call completes.

## Relationship to the other proposals

PD-10 uses the current typed tool contract. It does not replace any proposal
from PD-1 through PD-9.

| Proposal | Relationship to PD-10 |
|---|---|
| PD-1 | A local Executor call does not provide durable workflow state, events, timers, or restart-safe resume. |
| PD-2 | The MVP does not add idempotency keys, transactions, reconciliation, or mutation receipts. |
| PD-3 | Executor dispatch does not add confidentiality, integrity, or origin labels to ALLEN values. |
| PD-4 | Executor identity and policy do not provide the portable signed principals and receipts proposed by PD-4. |
| PD-5 | PD-5 may later replace manual catalog selection with typed interface negotiation. The concrete Executor dispatch adapter remains useful. |
| PD-6 | The MVP enforces one host deadline. It does not add source-controlled races, retries, quorum, or supervision. |
| PD-7 | Completed JSON values do not provide typed streams or authority-bearing artifact references. |
| PD-8 | Executor can expose memory services as tools, but it does not add ALLEN memory ownership, retention, concurrency, or provenance rules. |
| PD-9 | Tool dispatch does not add provider-independent model selection, privacy, cost, fallback, or review policy. |

PD-10 has no proposal dependency because its MVP can ship against the current
language and protocol. Future revisions may consume PD-2, PD-4, PD-5, PD-6,
and PD-7 contracts when those designs exist.

## Implemented MVP

1. The JOSH CLI parses `--executor` and repeatable `--grant-tool` options.
2. The runner validates tool grants against the frozen catalog before program
   execution and passes them through the existing artifact preflight.
3. The runner-side protocol client owns the Executor CLI provider.
4. The provider dispatches only `tool/invoke`; every other unsupported request
   stays on its current unavailable path.
5. Private temporary input and child-process I/O are bounded.
6. The provider enforces the request deadline and terminates the child on expiry.
7. Result decoding is strict and uses the fixed declared-error
   projection.
8. Focused CLI and fake-executor tests cover dispatch, denial, output bounds,
   deadline handling, shell separation, stderr redaction, and cleanup.

The MVP keeps the ALLEN language, artifact, replay, and `josh/1.5` wire
contracts unchanged.

## Acceptance contract

- Preserve current `josh run` behavior when `--executor` is absent.
- Reject a tool grant when `--executor` is absent.
- Reject a missing or non-executable `executor` command before entry execution.
- Invoke one fake Executor binary with an exact argument vector and no shell.
- Pass tool input through a user-only temporary file rather than process
  arguments.
- Remove the temporary input after success, failure, and timeout.
- Return and validate one successful object result.
- Return and validate one fixed declared error.
- Reject a mismatched declared-error schema before invocation.
- Reject a granted tool that is absent from the catalog.
- Reject a granted tool that the artifact does not declare.
- Deny an entry effect when its required tool lacks an exact grant.
- Reject malformed, multiple, trailing, and oversized CLI output.
- Fail closed on human-readable approval and authentication output.
- Kill the CLI child at the operation deadline.
- Do not retry after timeout or process loss.
- Keep raw stderr and temporary paths out of the public runtime error.
- Treat shell metacharacters in a valid UTF-8 tool segment as data, never as a
  command boundary.
- Replay a recorded tool result without starting the fake Executor binary.
- Preserve all existing stdio, tool-roundtrip, runner, and host conformance
  tests.
